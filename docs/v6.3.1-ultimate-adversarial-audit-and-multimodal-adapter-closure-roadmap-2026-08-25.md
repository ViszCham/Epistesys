### 結論

RPA-00〜39は、単なる将来ロードマップではなく、`lc631-analysis` crateと`lc631-rpa-doctor`経路として依存順に実装された。40 stageの存在、順序、依存、非Authority性、fail-closed release gateはコードとテストで固定されている。Rustでは実際の`rustc`からMIR、LLVM IR、assembly、objectを取得し、Pythonでは候補sourceを実行せずにAST、symtable、compile、code object、opcodeを観測し、Assemblyでは明示target/dialectの静的inventoryとRust codegen由来のassembly/object witnessを接続する。

ただし「配線済み」と「全外部証拠が観測済み」は同義ではない。Miri、fuzz、形式検証、multi-tool Assembly differential、runtime、host-final output、package、remote CI等の実receiptがないrunは、対応stageを`NeedsEvidence`または`Candidate`に保ち、`release_complete=false`とする。fixtureで正経路を通せることはgateの到達可能性を検査するだけで、実host、runtime safety、形式証明、repository-wide safety、release approvalを証明しない。

### v6.3.0優先・v6.3.1 shadow順序

実装判断は必ず次の順序で行う。

1. v6.3.0 full DecisionEnvelopeを不変ベースラインとして先に計算する。
2. v6.3.0のAuthority、Coding gate、Artifact/View、claim boundaryを読む。
3. v6.3.1 TLDG/RPA shadowを同じ課題に通し、差分と未接続面を列挙する。
4. mutationはv6.3.1 subtreeだけへ適用する。
5. meaningful diff後と最終時に、再びv6.3.0を先、v6.3.1を後の順で通す。

v6.3.1はv6.3.0を置換しない。v6.3.0のprotected-file digestは`lc631-v630-guard`で監査し、RPA-39はexpected baseline digestが一致しなければ閉じない。低Loss、test pass、Assurance結果、RPA wiringのいずれもMutationAuthorityやrelease authorityを生成しない。

### 敵対的修正で閉じた穴

1. source extensionがあるときはそれを言語scope ownerとし、prompt markerは異言語を追加できない。矛盾は`selection_conflicts`へ残す。
2. prompt markerだけの言語推定は`Candidate`であり、RPA-03を`Observed`へ昇格しない。
3. CLI source fileはregular fileかつ1MiB以下に限定する。Python/Assembly library entryにも1MiB上限を置く。
4. Cargo metadataは`--offline --no-deps`で、build script/proc macro/download/buildを実行しない。
5. tool version probeはstdout打切り時に`Observed`にならない。
6. Rust compiler invocationは同一crate-name競合を避けるためsource digest由来名とprocess-local lockを使う。
7. invalid Rust/Pythonは`Refuted`、backend不在は`Unavailable`、権限なしbuild scriptは`NotAuthorized`として区別する。
8. `NotApplicable`は未選択言語だけに使い、要求scopeの未観測を隠すために使わない。
9. stage completion receiptはdependency順、source revision一致、HostBound、unique stage、完全digest、unsupported空を要求し、`Refuted`を上書きできない。
10. RPA-39はRPA-00〜38、semantic reversal、directional loss、dead-fixture zero、v6.3.0 baseline、host output、package、remote CIが同時に揃わなければ閉じない。
11. stdout consumerが途中切断してもpanicせず、`stdout_write`診断とexit code 2でfail-visibleにする。

### 完成定義とResidualRiskLedger

source実装の完成条件は、RPA-00〜39が一意なDAGとしてCLI/doctorから到達でき、各backend結果が消費され、negative fixtureが誤昇格せず、外部receipt consumerがfail-closedであることとする。artifact/releaseの完成条件は別で、同一revision上の実validation、v6.3.0 baseline、exact host callback、package manifest、remote CI、requested-language runtime/ABI証拠を要求する。

残存riskは消去せず次を記録する。

- v6.3.0 full ArtifactとRPA reportのhost-signed import receiptは未接続。
- prompt-only language selectionはCandidateであり、repository manifest/compiler DB targetは未実装。
- Rust macro hygiene、crate-instance HIR、unsafe soundness、ABI、Miri、weak memory、formal proofは未観測。
- Python typing checker、import/runtime、free-threaded schedule、native extensionは未実行。
- explicit Assemblyのassemble/link/disassemble/emulate/native differentialは未実行。
- multimodal external backends、model/license、timestamp alignmentは未観測。
- exact host callback、durable replay、package install、remote CIはこのtaskで未実施。
- Assurance未監査範囲と`blocked_with_diagnostics`/`needs_evidence`を保持する。

したがって、現時点で主張できるのは「v6.3.1のRPA-00〜39 source配線と局所backend観測経路が完成し、外部証拠不足時にはrelease gateを未承認のまま閉じておく」ことである。「全弱点ゼロ」「全言語意味解析完成」「host-level enforcement」「形式証明」「release済み」は主張しない。

### Conclusion

RPA-00 through RPA-39 are no longer merely a future roadmap. They are implemented as the `lc631-analysis` crate and the `lc631-rpa-doctor` route in dependency order. Code and tests fix the existence, order, dependencies, non-authorizing character, and fail-closed release gate of all 40 stages. Rust retrieves actual MIR, LLVM IR, assembly, and object artifacts from `rustc`; Python observes AST, symtable, compilation, code objects, and opcodes without executing candidate source; Assembly connects explicit target/dialect inventory and Rust-codegen assembly/object witnesses.

However, “wired” and “all external evidence observed” are not synonyms. A run without real receipts for Miri, fuzzing, formal verification, multi-tool Assembly differential, runtime, host-final output, package, remote CI, and similar surfaces retains the corresponding stage as `NeedsEvidence` or `Candidate` and keeps `release_complete=false`. A fixture that reaches the positive contract path checks gate reachability only; it does not prove a real host, runtime safety, formal correctness, repository-wide safety, release approval, or delivery.

### v6.3.0-first, v6.3.1-shadow order

Implementation decisions always use this order.

1. Compute the v6.3.0 full DecisionEnvelope first as the immutable baseline.
2. Read v6.3.0 Authority, Coding gate, Artifact/View, and claim-boundary material.
3. Run the v6.3.1 TLDG/RPA shadow over the same task and enumerate differences and disconnected surfaces.
4. Apply mutations only inside the v6.3.1 subtree.
5. After meaningful diffs and at finalization, run v6.3.0 first and v6.3.1 second again.

v6.3.1 does not replace v6.3.0. The v6.3.0 protected-file digests are audited by `lc631-v630-guard`, and RPA-39 cannot close if the expected baseline digest differs. Low Loss, passing tests, Assurance results, and RPA wiring never create MutationAuthority or release authority.

### Holes closed by adversarial repair

1. When a source extension exists, it owns language scope; prompt markers cannot add another language. Contradictions remain in `selection_conflicts`.
2. Prompt-marker-only language inference is `Candidate` and cannot promote RPA-03 to `Observed`.
3. CLI source files must be regular files no larger than 1 MiB. Python and Assembly library entries also impose a 1 MiB limit.
4. Cargo metadata uses `--offline --no-deps` and runs no build script, proc macro, download, or build.
5. A truncated tool-version response cannot become `Observed`.
6. Rust compiler invocations use source-digest-derived crate names and a process-local lock to avoid same-name artifact races.
7. Invalid Rust/Python is `Refuted`, an absent backend is `Unavailable`, and unauthorized build-host code is `NotAuthorized`.
8. `NotApplicable` is only for an unselected language and cannot hide missing evidence in requested scope.
9. A stage-completion receipt requires dependency order, matching source revision, HostBound binding, a unique stage, a complete digest, and no unsupported items, and cannot overwrite `Refuted`.
10. RPA-39 cannot close unless RPA-00 through RPA-38, semantic reversal, directional loss, zero dead fixtures, the v6.3.0 baseline, host output, package, and remote CI all agree.
11. If a stdout consumer disconnects early, the CLI fails visibly with a `stdout_write` diagnostic and exit code 2 instead of panicking.

### Completion definition and ResidualRiskLedger

Source implementation is complete when RPA-00 through RPA-39 are reachable from CLI/doctor as one unique DAG, every backend result is consumed, negative fixtures do not mis-promote, and external-receipt consumers fail closed. Artifact/release completion is separate and requires real validation on one revision, the v6.3.0 baseline, an exact host callback, a package manifest, remote CI, and requested-language runtime/ABI evidence.

Residual risks are retained rather than erased.

- A host-signed import receipt between the v6.3.0 full Artifact and the RPA report is disconnected.
- Prompt-only language selection is Candidate; repository-manifest/compiler-database target selection is unimplemented.
- Rust macro hygiene, crate-instance HIR, unsafe soundness, ABI, Miri, weak memory, and formal proof are unobserved.
- Python type checking, imports/runtime, free-threaded schedules, and native extensions are not executed.
- Explicit Assembly assemble/link/disassemble/emulate/native differential is not executed.
- Multimodal external backends, model/license bindings, and timestamp alignment are unobserved.
- Exact host callback, durable replay, package installation, and remote CI were not performed in this task.
- Assurance-unreviewed scope and all `blocked_with_diagnostics`/`needs_evidence` states are retained.

The defensible claim is therefore: “the v6.3.1 RPA-00 through RPA-39 source wiring and local backend-observation paths are complete, and the release gate remains closed and unapproved when external evidence is missing.” It does not claim “zero weaknesses,” “complete semantic analysis for every language,” “host-level enforcement,” “formal proof,” or “released.”
